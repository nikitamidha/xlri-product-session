§1 · Many agents1:00 — 4:30

Several agents, different jobs, one objective

Same task both ways: "review this 60-page vendor contract against our policy."

One agent

Reads the contract and the policy, works through it, writes the findings.

Good: it has seen everything, so it catches clause 4 contradicting clause 31. One trace. Cheap.

Bad: sixty pages plus the policy fills its head; quality sags by page fifty; one point of view, and it marks its own work.

Several agents

An orchestrator splits the contract into four sections → four readers, each holding the policy and one section → a critic tries to knock down every finding → the orchestrator merges what survives.

Good: nothing gets skimmed, and the findings were attacked by something with no stake in them.

Bad: roughly six times the cost, and nobody has read the whole contract — so clause 4 versus clause 31 is exactly what this version misses.

The second is not the upgrade. It trades one kind of blindness for another — and which blindness you can live with is the actual product decision.

Four shapes, and what each is for

ShapeHow it runsUse it for
Manager and workersOne splits the job, hands out pieces, merges the resultsBreadth — searching, reviewing, auditing many things at once

Why the critic works

An agent that grades its own output grades generously — for the same reason you cannot proofread your own writing. A second agent, told to refute rather than to help, catches what the first one structurally cannot see.

§2 · Harness4:30 — 8:00

The harness: the code that turns a model into an agent

The model only ever does one thing — read text, write text. Everything else in the loop is ordinary software somebody wrote, and that software is the harness.

The harness — one turn of the loop
gather what it needs to know→ MODEL→ read what it asked for→ actually run the tool→ hand back the result
and all the way round: the rules of the run
step limitspend capwhich tools it may touch what to do on an errorwhen it's finishedrecord everything

You have already used several

Claude Code and Cursor's agent mode are harnesses. So is the fifty-line Python loop your engineer wrote last month. The interesting engineering in this field is mostly here, not in the model.

Why a PM should care

Same model, different harness, completely different capability. Two coding agents on the identical model are not equally good, and the gap is context assembly, tool design and error handling.

The model is available to your competitor at the same price. The harness is not.

§2 · Orchestrator4:30 — 8:00

The orchestrator: who decides which agent does what

Two kinds, and the difference matters

Orchestration in code. You wrote the split — always four sections, always a critic. Predictable, testable, boring, usually right.

Orchestration by a model. A manager agent decides at run time how to break the job up and who gets what. Flexible — and now the who-decides question from last class applies one level up.

What the orchestrator is actually responsible for

Splitting the work · giving each worker only what it needs · setting each one a budget · merging results · deciding what happens when two workers disagree or one fails · keeping one record of the whole run.

A "multi-agent system" whose fan-out is hard-coded is a workflow of agents — and that is usually good news. The orchestrator is also the accountability point: if nothing owns the merge, nobody owns the answer.

Start with one agent. Split only when something forces you.

AskIf yesBecause
Would this sub-task bury the main thread in material it doesn't need afterwards?SplitA reader that swallows forty pages and returns eight lines keeps the main agent sharp
Does part of this need different permissions, or a smaller blast radius?SplitThe agent that can pay money should not also be the one browsing the open web
Do you need a check from something with no stake in the answer?SplitThat is the critic, and it is the one split that reliably pays
Are the parts genuinely independent, and is the wait hurting?SplitTen files reviewed at once instead of one after another
None of the aboveStay unifiedOne agent with more tools beats many agents with fewer, nearly every time

What staying unified buys you

It remembers what it already tried. Nothing is lost at a handoff. One trace to read when it goes wrong. One thing to hold accountable. And it costs a fraction as much.

§3 · One or many8:00 — 11:00

More agents usually means less reliability

Errors multiply, they don't average

0.9510 ≈ 60%

Ten handoffs, each 95% right, and the run is a coin toss.

Every handoff loses context

The real gain from AI was that the person holding the context now does the work — nothing is lost explaining it to someone who wasn't in the room.

A badly split system puts that loss straight back. You have rebuilt the org chart, including the parts of it that don't work.

Cost and waiting multiply

Six agents is roughly six times the bill, and the slowest one sets the clock.

Nobody to ask

Five agents, one bad answer, and no single place where it went wrong.

§3 · One or many8:00 — 11:00

Rules of thumb

Do

  • Give one agent more tools before you give two agents fewer.
  • Keep the join narrow — a worker returns a short structured result, not a conversation.
  • One level deep. Workers that spawn workers cannot be debugged.
  • Hard-code the split wherever you already know it.
  • Give every agent a budget: steps, tokens, money, minutes.
  • Keep one record for the whole run, not one per agent.

Don't

  • Don't mirror the org chart. Five human roles is not five agents.
  • Don't split for neatness — only for context, permissions, judgement or speed.
  • Don't let two agents write to the same thing.
  • Don't add a second agent to patch a first one you specified badly. That is a prompt problem wearing a costume.

Add an agent only when it needs a different context, different permissions, independent judgement, or genuine parallelism. Those four. Nothing else.

§4 · Seeing it11:00 — 14:30

Observability: being able to play back what it actually did

An agent works while nobody is watching, and it goes wrong in the middle rather than at the end. The recording is the only thing that exists afterwards.

What did it do?

The steps, in order. Every tool it used and what came back.

Why did it do that?

What it had been told and what it had found at that moment. The answer is nearly always here — and this is the part teams record last.

What did it cost?

Money, time, and every call it made to something that bills you.

Without it

Every bug report is "it did something odd on Tuesday", and there is nothing to look at. You cannot fix it, and you cannot promise anyone it won't happen again.

§4 · Seeing it11:00 — 14:30

This is all it is

09:14:02 ticket #4821 arrives — "parcel arrived damaged, want a refund"
09:14:03 looked up the customer → 14 orders, no previous refunds
09:14:04 read the refund policy → clause 3.2, damage in transit
09:14:05 looked up the order → delivered 2 days ago, ₹1,240
09:14:06 decided: refund → "within 30 days, damage reported on arrival, clause 3.2"
09:14:07 called the refund API ₹1,240 → success, ref RF-88213
09:14:07 replied to the customer
5 steps · 8 seconds · ₹0.42 of model calls · no human involved

What this gives the customer team

An answer to "why did it refund that?" in ten seconds, with the clause it relied on. A complaint becomes a fix instead of an argument.

And when it's wrong

You can see which step was wrong — not just that the run was. Usually it is line three: it read the wrong policy, or the right one badly.

§4 · Seeing it11:00 — 14:30

The recording has three audiences. Teams build one.

WhoWants it forNeeds to see
The engineerFixing itEverything, raw
The userDeciding whether to trust it — and eventually whether to stop watchingA readable account of what was done, with any step openable
The organisationAnswering for itWho allowed what, when, under which policy — and kept

The loop this makes with evals — and it is the whole engineering process

something goes wrong in production → you can see which step → that becomes a new case on the question paper → the fix is checked against every old case too → shipped → watched again

The recording tells you what happened. The evals tell you whether it's getting better. Recordings without evals is archaeology; evals without recordings is a score you can't diagnose.

§5 · Workforce14:30 — 17:00

A role is a bundle of jobs. Agents don't replace roles — they unbundle them.

"Analyst" is not a unit of work. It is thirty jobs bundled together because they happened to need the same person, in the same place, with the same context. Take the bundle apart first, then ask.

A PM's own weekWhere it goesWhy
First draft of the PRDAugmentThe draft is cheap now; the argument still isn't
Chasing status across five teamsAutomateBounded, checkable, and nobody ever wanted to do it
The weekly status deckAbandonIt existed because gathering information was expensive. It isn't any more.
Deciding what not to buildHumanAccountability, and taste
Telling someone their project is cancelledHumanDelegating it is the message

Abandon is the biggest category and the least claimed

A lot of corporate work is the residue of a constraint that has gone — reporting, formatting, re-keying, summarising for people who couldn't attend, chasing. Automating that work preserves it. Ask first whether it should exist at all.

§5 · Workforce14:30 — 17:00

What stays human, stated precisely

  • Accountability. An agent cannot be answerable. Somebody must be — that is a legal and social fact, not a gap in the technology.
  • Setting the standard. What "good" means here is the input to everything the agents do.
  • The reasons nobody wrote down. Including the ones nobody would write down.
  • Consent and relationships. Who gets told what, by whom, in what order.
  • The case that is genuinely new. Not like the last thousand.
Managers measuredNow measure
HeadcountCost per finished job
UtilisationHow much finishes untouched
Cycle timeHow often it escalates, and how long checking takes
DefectsHow much comes back after being accepted

None of these exist unless something is recording the work. Half this workforce files no timesheet and never complains.

Two traps: pair every agent with a reviewer and the reviewer becomes the bottleneck. And output grows faster than anyone's ability to check it — which is the same thing, one quarter later.

The same instrument, pointed at agents

ForceAn assistantAn agent
PUSH — what's going badlyI write more than I can typeNew, and self-inflicted: assistants let me generate more work than I can execute or check
PULL — what I can pictureVivid. "It writes the thing"Weak. "It'll do it while you're not watching" is hard to imagine — and a good agent's demo is nothing happening

Push + Pull must beat Anxiety + Habit

For agents the two forces holding it back are anxiety and habit, and both belong to the organisation, not the person. What blocks an agent sale is almost never capability — it is that nobody can say who is accountable when it's wrong, and the existing process has no slot for it.

Which is the good news: those are the two forces a product team can actually work on. Recordings, dry runs, sandboxes, scoped permissions, spend caps, undo, gates, and an eval number you can show a buyer — and fitting the approval chain that already exists rather than replacing it.

The job never changed. The standard did — twice.

EraWhat the user will accept
Before generative AIOutput I can work with
AssistantsOutput I can send without editing
AgentsWork I didn't have to watch

Which rewrites the job story, once the work is delegated rather than done

When [circumstance], I want [the agent] to [do this], so I can [outcome] — and I'll accept it without checking when [condition].

That last clause is the product specification. Ask it of any agent product; most teams have never written the condition down.

What moved is the standard — which is exactly what jobs-to-be-done tells you to look at, and exactly what a feature list never shows you.

Close · back to jobs to be done17:00 — 20:00

Seven questions for any agentic product

  1. What job is being handed over, and at what rung? Not "what does it do" — what progress is a person no longer making themselves?
  2. What's the unit of work, and how does the user know it's finished? No definition of done, no agent — just a process that never ends.
  3. Where's the last moment you could still undo it, and what happens there?
  4. How does the user check it without redoing it? If checking costs as much as doing, nothing has been handed over.
  5. What does it do when it doesn't know? Show me that path, or the failure mode is confident invention.
  6. How would you know it got worse? Which cases, marked how, watched by whom.
  7. Who is accountable when it's wrong — and does the product make that person's job possible? The question that closes agent deals, and the one teams answer last.
The closing question

Agents put more work in flight than anyone can supervise.

Generative AI created a new push by making us produce far more language than we ever have. Checking was already the bottleneck for code. It is about to be the bottleneck for everything an organisation does.

Where is the product for that side of the exchange?
