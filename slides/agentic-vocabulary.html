LLM

A model that has read an enormous amount of text, and given some text, writes what should come next

The version that matters commercially: it follows instructions nobody programmed in advance. Software before 2022 could only do what someone had specified. This does things its builders never listed.

It has no memory

Every call starts from zero. Anything it knows about your situation, somebody put in front of it just now.

So: getting the right material in front of it is the actual product.

It isn't exact

Ask the same thing twice, get two different answers. Both may be fine. One may be confidently wrong.

So: you can't test it the way you test software.

It has no hands

It writes. It cannot click, send, pay, book or remember.

So: on its own it can only tell you things.

It can advise. It cannot act.

LLM

Three things an LLM is not

Not a chatbot

Chat is a screen that was easy to build around the model. It was the first interface, not the right one.

Not a search engine

It does not look anything up. It writes what plausibly comes next. When the plausible thing is false, nothing has malfunctioned — which is exactly why products bolt on sources and citations.

Not normal software

"It worked when I tried it" is not a test result. It is one sample, reported by the person most motivated to like it.

The test

If the only thing that comes out is words on a screen for a person to read and act on, you have an LLM product, not an agent. Often the right answer — and a completely different design problem.

Agent

An LLM in a loop: given a goal, it picks an action, sees what happened, and decides what to do next — including when to stop

It needsOr else
A goalIt never finishes — nothing defines "done"
ToolsIt can only describe what it would do
Memory of the runIt solves the same problem again every step
The loopOne shot, no recovery from a bad step
A way to stop or askIt runs forever, or fails quietly

An agent with no way to say "I don't know" will invent its way past the uncertainty.

Agent

Tools, skills, context — what an agent is actually made of

PartWhat it isIf it were a new hire
ToolsWhat it can do. Each one is a function you expose to it with a name and a description — search, read a file, look up an order, issue a refund, send an emailThe systems access you give them on day one
SkillsHow you want it done. Packaged instructions for a task — the procedure, the standard, the examples, the house style — loaded only when relevantThe onboarding docs and the way-we-do-it-here playbook
ContextWhat it knows right now. The instructions, the conversation so far, whatever material was fetched for this task, and what the tools returnedWhat is on their screen at this moment

Tools are permissions

The list of tools is the blast radius. And the model never runs a tool itself — it asks, and the code around it decides whether to comply.

A skill is usually just a document

Written instructions for how your company does a thing, plus a line saying when to use them. No model training, no engineering. Which makes "who writes it" an organisational question, not a technical one.

Context is finite, and fresh every turn

It is rebuilt from scratch on every step, and it runs out. More is not better — a stuffed context makes the thing duller, not smarter.

The model is everyone's — your competitor rents the same one. Your tools, your skills and your context are not.

Human in the loop

Ask someone to approve two hundred correct actions and they will approve the wrong one

This is well documented long before AI — aviation, radiology, freight. People do not stay sharp watching something that is nearly always right.

Fewer gates

A gate a person cannot keep up with gets removed by somebody, officially or otherwise.

Evidence at the gate

Show the diff, the source, the amount, the customer. An approval box with nothing to check produces rubber-stamping.

Or make it reversible instead

Gmail's undo send is not an approval — it is a thirty-second window in which the action can be taken back. It replaced a gate nobody would have tolerated.

A gate approved 99% of the time is not a control. It is a ritual — and it hands liability to a person who was never really able to check.

Evals

A set of test cases with known good answers, re-run every time you change something

The plain version

A question paper you keep. Every time you change the prompt, the model or the tools, you re-take it.

You are not looking at the score. You are looking at which way it moved.

Why you can't skip it

The system is different every run. You cannot tell whether a change helped by trying it once — you'd be sampling, and calling it evidence.

Every team without one relearns the same failure every quarter and calls it bad luck.

Who marks the paper

A script, when the answer is checkable — did it call the right tool, is the number right, did it stay under budget. Cheap and exact.
Another model, for things like tone and completeness. Cheap, scales, and needs checking against human marks — an unmarked marker is a rumour.
A person, for the hard cases. Expensive: use them to set the standard, not to run the paper.

Evals

For an agent, the right answer is not enough

Outcome — did it end up right?

The refund is correct. ₹1,240, to the right customer, with the right reason recorded.

Route — would you accept how it got there?

It read every customer record to decide, took forty steps, spent ₹900 in model calls doing it, and never escalated the one case it should have.

And this is how a team earns the right to stop watching

You do not let an agent run unsupervised because the demo went well. You let it because the pass rate on your own cases, for that kind of task, is high enough that the failures left are ones you can afford.

Grade only the outcome and you are training a system to be lucky. You don't ship an agent because it worked — you ship it because it stopped failing where it used to, and you can show the number.

Agile assumed four things. All four stopped being true.

SDLC assumedWhat is true now
Producing code is the expensive stepAn attempt costs almost nothing — and is disposable
Code is the artifact of recordThe spec is. Code is a regenerable output
Same input, same outputThe same input can give a different answer. A bug has a rate, not a reliable way to reproduce it
However much got written, someone could read it allOne human, several agents, each faster than you read

Every ceremony in Agile protects you from committing to the wrong code. That was the expensive act. It isn't any more.

Two questions to take back

The artifact test

Delete the code, keep the specs — could you rebuild?

Delete the specs, keep the code — could you?

Whichever answer is yes tells you which lifecycle you are actually running.

The bottleneck test

Name where your team's time actually goes.

Still writing code? The tools changed and the process didn't.

Reviewing and verifying? Then that is where the investment belongs.

Which is why the last twenty minutes were about evals

Verification is the new bottleneck, and it is a human one — it does not fall with the next model release. Evals are how you buy it back.

If machines ever verify machines, the last bottleneck standing is knowing precisely what should exist — and that was never an engineering skill.
